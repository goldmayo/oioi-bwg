# ENGINEERING_PRINCIPLES.md

# Engineering Principles

> 목표는 단순히 코드를 잘 작성하는 것이 아니다.
> **변경하기 쉽고, 이해하기 쉽고, 실패에 강하며, 지속적으로 운영할 수 있는 제품을 만드는 것​**이다.

---

## 1. 좋은 코드 품질이란 무엇인가

좋은 코드는 단순히 깔끔하거나 추상화가 잘된 코드가 아니다.

다음 질문에 긍정적으로 답할 수 있어야 한다.

- 변경하기 쉬운가?
- 문제의 원인을 찾기 쉬운가?
- 처음 보는 팀원이 이해하기 쉬운가?
- 테스트하기 쉬운가?
- 실패했을 때 영향 범위가 제한되는가?
- 사용하는 라이브러리와 프레임워크의 관례를 따르는가?
- 실제 운영 환경에서 관찰하고 대응할 수 있는가?

코드 품질은 결국 **변경 비용과 운영 비용을 얼마나 낮추는가**로 평가한다.

---

## 2. 추상화와 아키텍처의 기본 원칙

아키텍처는 복잡함을 보여주기 위한 것이 아니라 복잡함을 관리하기 위한 것이다.

새로운 구조나 추상화를 만들기 전에 항상 묻는다.

> 이 추상화가 정말 필요한가?

> 이 구조를 처음 보는 사람이 이해할 수 있는가?

> 6개월 뒤 다른 개발자가 유지보수한다고 해도 이 구조가 여전히 필요한가?

기본 원칙은 다음과 같다.

- 어휘세를 낮춘다.
- 바퀴를 다시 만들지 않는다.
- 라이브러리의 공식 API를 우선한다.
- 프레임워크의 관례를 존중한다.
- 현재 존재하지 않는 문제를 해결하기 위한 아키텍처를 만들지 않는다.
- 커스텀 abstraction보다 표준적인 패턴을 먼저 검토한다.
- 복잡성을 추가할 때는 얻는 이득을 명확히 설명할 수 있어야 한다.

좋은 추상화는 보통 실제 반복과 변경 패턴을 발견한 뒤 나온다.

```text
문제를 직접 해결
    ↓
반복과 변경 패턴 발생
    ↓
공통점 발견
    ↓
필요한 만큼만 추상화
```

반대로 다음 흐름은 경계한다.

```text
미래에 필요할 것 같음
    ↓
추상화 설계
    ↓
자체 프레임워크 생성
    ↓
모든 코드가 구조에 종속
```

## 3. 공유 코드의 원칙

여러 애플리케이션이나 플랫폼에서 모든 코드를 공유하는 것이 목표가 되어서는 안 된다.

**변화의 이유가 같은 것만 공유한다.**

공유 가치가 높은 영역은 다음과 같다.

- API contract
- Zod schema
- domain type
- business rule
- validation
- query key
- 재사용 가치가 명확한 일부 query / mutation logic

반대로 UI와 플랫폼 동작은 억지로 공유하지 않는다.

공유 코드가 플랫폼별 예외 처리와 조건문으로 가득해지기 시작하면 공유의 이점보다 결합 비용이 커지고 있다는 신호다.

---

## 4. 기술 선택은 요구사항에서 시작한다

익숙한 기술을 먼저 선택한 뒤 문제를 끼워 맞추지 않는다.

특히 웹과 모바일 멀티플랫폼 개발에서는 먼저 제품 요구사항을 확인한다.

- 네이티브 기능이 얼마나 필요한가?
- 성능 요구 수준은 어느 정도인가?
- App Store / Play Store 배포가 필요한가?
- 오프라인 동작이 필요한가?
- Push Notification이 필요한가?
- Deep Link가 필요한가?
- 카메라, 파일 시스템 등 네이티브 API가 필요한가?
- 모바일 UI와 웹 UI가 얼마나 다른가?
- 팀은 어떤 기술에 강한가?
- 장기적으로 누가 유지보수할 것인가?

그 다음 기술을 비교한다.

```text
제품 요구사항
    ↓
플랫폼 제약
    ↓
팀 역량
    ↓
대안 비교
    ↓
가장 단순한 해결책 선택
```

기술은 목적이 아니라 제약을 해결하기 위한 수단이다.

---

## 5. 프론트엔드 아키텍처는 책임의 경계를 정하는 일이다

프론트엔드 아키텍처는 디렉터리 구조를 예쁘게 만드는 일이 아니다.

핵심은 **어떤 책임을 어디에서 끝낼 것인가**를 정하는 것이다.

SPA를 설계할 때는 다음을 고민한다.

- FSD를 어디까지 적용할 것인가?
- API layer의 책임은 어디까지인가?
- Query / Mutation error를 어떻게 통일할 것인가?
- Zod contract는 어디에 둘 것인가?
- server state와 client state의 경계는 어디인가?
- CI에서 lint / typecheck / test / build를 어떻게 검증할 것인가?
- PR 전에 어떤 regression을 자동으로 잡을 것인가?
- loading / error / empty state를 어떻게 일관되게 표현할 것인가?
- 인증과 권한 처리는 어느 레이어에서 담당할 것인가?
- observability를 어떻게 확보할 것인가?

SSR 애플리케이션이라면 추가로 다음을 고려한다.

- RSC
- hydration
- server / client boundary
- cache
- revalidation
- runtime
- streaming
- deployment
- observability

SSR을 사용한다는 것은 단순히 서버에서 HTML을 생성한다는 뜻이 아니다.

렌더링 위치, 캐시 정책, 데이터 freshness, runtime, deployment까지 모두 애플리케이션 설계의 일부가 된다.

## 6. 시니어 엔지니어의 문제 해결 방식

좋은 엔지니어는 실수를 하지 않는 사람이 아니다.

실수가 발생했을 때 다음 흐름을 만든다.

```text
실수
 ↓
원인 파악
 ↓
책임 인정
 ↓
복구
 ↓
재발 방지
```

개인의 주의력만으로 문제를 해결하려 하지 않는다.

잘못된 질문:

> 누가 이 실수를 했지?

더 좋은 질문:

> 왜 우리의 프로세스가 이 실수를 허용했지?

좋은 시스템은 사람에게 계속 조심하라고 요구하기보다 **실수하기 어렵게 만든다.**

## 7. Engineering Discipline

좋은 아키텍처만으로 좋은 제품이 만들어지지는 않는다.

일상적인 개발 discipline이 중요하다.

- PR을 작게 나눈다.
- `main`을 보호한다.
- release 절차를 만든다.
- rollback 방법을 알고 있다.
- migration 순서를 신경 쓴다.
- 다른 사람의 작업을 불필요하게 깨뜨리지 않는다.
- 배포 전 regression을 자동으로 검증한다.
- 사고가 발생하면 책임자가 앞으로 나온다.
- 사고 이후 원인과 재발 방지책을 남긴다.

배포 사고가 발생했다면 단순히 코드를 고치고 끝내지 않는다.

다음을 확인한다.

- 무엇이 실패했는가?
- 왜 사전에 발견하지 못했는가?
- 왜 배포까지 통과했는가?
- 어떤 자동화가 있었다면 막을 수 있었는가?
- 같은 사고가 다시 발생하지 않게 무엇을 바꿀 것인가?

---

## 8. 혼자 개발할 때는 의도적으로 자신을 리뷰한다

혼자 개발하면 의사결정 속도는 빨라진다.

대신 자연스럽게 발생하는 코드 리뷰와 반대 의견이 사라진다.

따라서 스스로 다음 질문을 반복한다.

> 이 추상화가 정말 필요한가?

> 라이브러리 기본 기능으로 해결할 수 없는가?

> 이 구조를 처음 보는 사람이 이해할 수 있는가?

> 지금 해결하고 있는 문제는 실제 문제인가?

> 미래를 상상해서 문제를 만들고 있지는 않은가?

> 이 코드는 삭제하기 쉬운가?

> 장애가 발생하면 어디서 확인할 수 있는가?

> 더 단순하게 만들 수 있는가?

# AI-Assisted Engineering

## 9. AI 시대의 디버깅

AI에게 디버깅을 맡기는 것이 아니다.

**AI를 이용해 탐색 공간을 빠르게 압축한다.**

권장 흐름은 다음과 같다.

```text
에러
+
관련 코드
+
로그
+
환경 정보
        ↓
가능한 원인 여러 개 생성
        ↓
가능성 순위 매김
        ↓
직접 빠르게 검증
        ↓
공식 문서 / Issue / Source Code 확인
        ↓
최소 범위 수정
        ↓
Regression Test 추가
```

AI의 역할은 정답을 대신 결정하는 것이 아니라 **가설 생성 비용을 낮추는 것**이다.

최종 판단과 검증 책임은 개발자에게 있다.

---

## 10. AI로 생산성을 높이는 영역

AI는 반복 작업과 탐색 비용을 줄이는 데 적극적으로 사용한다.

### 반복 작업

- 단순 CRUD
- 테스트 boilerplate
- Storybook story
- mock / fixture
- 반복적인 변환 코드

### 학습

낯선 라이브러리를 접했을 때:

```text
공식 문서
   ↓
AI로 핵심 압축
   ↓
필요한 부분 원문 확인
   ↓
직접 구현
```

### 디버깅

에러와 관련된 코드, 로그, 환경 정보를 한 번에 제공하고:

- 가능한 원인 후보를 생성하게 한다.
- 가능성이 높은 순서로 정렬하게 한다.
- 확인해야 할 지점을 찾게 한다.

### 코드 리뷰

PR 전에 다음을 묻는다.

> 이 변경으로 깨질 수 있는 경계를 찾아줘.

> 이 설계에서 숨겨진 coupling을 찾아줘.

> 라이브러리 기본 기능으로 제거할 수 있는 커스텀 코드를 찾아줘.

> 더 단순하게 만들 수 있는 부분을 찾아줘.

### 설계

구현 전에 대안을 강제로 비교한다.

> 이 문제를 해결할 수 있는 방법을 3개 제안하고 각각의 trade-off를 비교해줘.

하나의 아이디어를 바로 구현하기보다 **대안을 먼저 펼쳐놓고 선택한다.**

## 11. AI에게 의도적으로 반대 의견을 요청한다

혼자 개발하는 환경에서는 사람 리뷰어가 부족하다.

AI를 동의해주는 도구보다 **반대편 리뷰어**로 활용한다.

예:

> 이 설계를 비판해줘.

> 이 구조를 처음 보는 3년차 개발자가 어려워할 부분을 찾아줘.

> 라이브러리 기본 기능으로 없앨 수 있는 커스텀 코드를 찾아줘.

> 운영 장애 관점에서 실패 시나리오를 찾아줘.

> 내가 지나치게 추상화한 부분을 찾아줘.

> 이 구현을 유지보수해야 하는 사람의 입장에서 문제점을 찾아줘.

AI에게 동의를 구하기보다 **내 판단을 공격하게 만드는 것**이 더 가치 있다.

---

## 12. AI가 제안하는 과설계를 경계한다

AI가 제안하는 패턴과 추상화는 상당히 그럴듯할 수 있다.

하지만 그럴듯하다는 것과 필요한 것은 다르다.

특히 다음 흐름을 경계한다.

```text
문제
 ↓
AI
 ↓
Factory
Strategy
Adapter
Manager
Provider
Wrapper
Custom Hook
Custom Framework
```

패턴 이름이 많아졌다고 설계 품질이 좋아지는 것은 아니다.

새로운 구조를 제안받았다면 다시 묻는다.

- 이것 없이 구현하면 어떤 문제가 생기는가?
- 라이브러리 공식 API만 사용하면 해결할 수 없는가?
- 실제 요구사항 때문에 필요한 것인가?
- 코드가 실제로 얼마나 단순해지는가?
- 새로 배워야 할 프로젝트 전용 개념은 얼마나 늘어나는가?

**어휘세가 증가하면 그 비용을 정당화할 만큼의 이점이 있어야 한다.**

# Learning

## 13. 거인의 어깨 위에서 개발한다

학습의 기본 흐름은 다음과 같다.

```text
원전
 ↓
AI
 ↓
코드
```

AI를 원전의 대체재로 사용하지 않는다.

AI는 **원전을 더 빠르게 읽고 이해하기 위한 가속기**로 사용한다.

예를 들어 TanStack Query라면:

- 공식 Documentation
- API Reference
- Maintainer의 설명
- GitHub Issues / Discussions
- 필요하면 Source Code

순으로 내려간다.

React라면:

- React 공식 Documentation
- 공식 Blog
- RFC
- GitHub Issues
- Source Code

TypeScript라면:

- Handbook
- Release Notes
- TSConfig Reference
- GitHub Issues

라이브러리가 이상하게 동작한다면 마지막에는 Source Code까지 내려갈 수 있어야 한다.

AI에게는 다음을 묻는다.

> 이 문서의 핵심 개념을 정리해줘.

> 우리 구조에 적용하면 어떤 선택지가 있어?

> 이 설계가 라이브러리의 공식 API 철학과 어긋나는 부분이 있어?

> 공식 문서에서 이 판단을 뒷받침하는 근거를 찾아줘.

# Growth

## 14. 반면교사를 넘어서 좋은 사례를 흡수한다

초기에는 잘못된 것을 피하는 능력이 중요하다.

```text
잘못된 코드 피하기
잘못된 추상화 피하기
과설계 피하기
```

하지만 그다음 단계에서는 다른 능력이 더 중요해진다.

```text
좋은 설계 발견하기
좋은 라이브러리 활용하기
좋은 팀의 패턴 이해하기
공식 API 철학 이해하기
운영 경험 흡수하기
```

이제는 다음 질문이 더 중요하다.

> **검증된 좋은 방법을 얼마나 빠르게 발견하고 흡수할 수 있는가?**

반면교사만으로 성장하는 데에는 한계가 있다.

좋은 엔지니어, 좋은 코드베이스, 좋은 라이브러리의 설계 방식을 적극적으로 관찰한다.

---

## 15. 목표는 제품 프론트엔드를 주도할 수 있는 엔지니어다

목표는 단순히 React 코드를 빠르게 작성하는 개발자가 아니다.

다음과 같이 설명할 수 있는 엔지니어를 지향한다.

> **FE 아키텍처, API contract, CI, 테스트 전략, UX consistency를 독립적으로 설계하고 운영할 수 있다.**

이를 위해 UI 구현 능력 외에도 다음 영역을 함께 키운다.

```text
                    Product FE
                        │
      ┌─────────────────┼─────────────────┐
      │                 │                 │
Architecture       Product UX        Operations
      │                 │                 │
API Contract       Loading           CI/CD
State Boundary     Error             Testing
Validation         Empty State       Observability
Caching            Accessibility     Deployment
Rendering          Consistency       Incident 대응
```

프론트엔드의 책임 범위를 브라우저 안으로만 제한하지 않는다.

제품이 실제 사용자에게 전달되고 운영되는 전체 흐름을 이해한다.

---

## 16. AI는 코딩 머신이 아니라 사고 가속기로 사용한다

AI의 가장 큰 가치는 코드 생성 자체에 있지 않다.

다음 역할로 활용한다.

- Senior Pair Programmer
- Search Accelerator
- Reviewer
- Devil's Advocate

지향하는 흐름은 다음과 같다.

```text
AI가 탐색
AI가 비교
AI가 반론
AI가 리뷰
AI가 반복 작업 처리
        ↓
개발자가 더 중요한 판단에 집중
        ↓
생산성 + 설계 품질 향상
```

최종 판단은 계속 개발자가 가져간다.

# Final Checklist

설계나 구현을 시작하기 전에 마지막으로 확인한다.

## Architecture

- 이 구조가 실제 문제를 해결하는가?
- 더 단순한 방법은 없는가?
- 공식 API로 해결할 수 없는가?
- 팀이 새롭게 배워야 할 어휘가 얼마나 늘어나는가?

## Maintainability

- 6개월 뒤 다른 개발자가 이해할 수 있는가?
- 변경 범위가 예측 가능한가?
- 테스트하기 쉬운가?

## Failure

- 실패하면 어디까지 영향이 가는가?
- 장애를 발견할 수 있는가?
- rollback할 수 있는가?

## Product

- loading / error / empty 상태가 정의되어 있는가?
- 사용자가 실패를 이해하고 복구할 수 있는가?
- UX가 다른 화면과 일관적인가?

## AI

- AI가 제안한 내용을 직접 검증했는가?
- 공식 문서를 확인했는가?
- 반대 의견도 요청했는가?
- AI가 불필요한 추상화를 추가하지 않았는가?
