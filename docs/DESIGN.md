# UI·UX 디자인 원칙

어이어이바위게의 공개 웹과 Console에서 화면을 구성하고 움직임을 결정할 때 쓰는 기준이다. 제품 화면을 설계하거나 리뷰하는 사람이 관리한다. 검증을 거쳐 채택한 규칙과 예외가 바뀔 때 갱신한다. 서비스 태도와 말투는 [서비스 철학](PHILOSOPHY.md), 상태의 정의와 전이는 [도메인 명세](migration/DOMAIN_SPECIFICATION.md), 구현과 접근성 검증은 [프런트엔드 아키텍처](migration/oioi-bwg-architecture-clean-v1/02-frontend-architecture.md)를 따른다.

이 문서는 반복 사용하는 디자인 생성·검수 절차의 정본이다. [AGENTS](../AGENTS.md)의 시작 절차를 통해 매 작업에서 읽고, 디자인 작업에서는 아래 생성 절차와 검수표를 사용한다. 헌법·active architecture·도메인 계약을 대체하지 않으며, 충돌 시 해당 계약을 따른다. 화면별 기능 명세와 토큰 값을 이곳에 복제하지 않는다.

## 디자인 철학

- 공개 웹은 팬이 자기 방식으로 응원에 합류하도록 돕는다. 재생 화면에서는 지금 읽을 줄과 참여할 부분에 가장 높은 시각적 우선순위를 준다.
- Console은 관리자가 대상을 빨리 찾고 작업 결과를 정확히 이해하도록 돕는다. 목록에서는 곡명·공연 모드·출처·공개 상태의 위치를 일관되게 유지한다. 편집과 공개는 각각의 결과가 드러나는 이름과 상태로 안내한다.
- 사용자가 작업을 이어갈 수 있게 현재 위치, 입력한 내용, 적용한 조건을 보존한다. 저장에 실패하면 원인과 다음 행동을 알리고 고칠 수 있는 위치를 연결한다.

## 시각 문법

- 반복해서 읽는 목록은 열 정렬과 일정한 행 간격으로 정보를 비교하기 쉽게 만든다. 곡명을 먼저 읽히게 하고 앨범명은 보조 정보로 배치한다. 긴 한글 제목과 좁은 화면에서 줄바꿈·말줄임을 확인한다.
- 제목, 검색, 필터, 결과는 한 흐름으로 읽혀야 한다. 데스크톱 목록에서는 기존 인라인 컨트롤을 사용한다. 모바일 상세 필터는 하단 시트에서 초안을 편집하고 **적용**을 누를 때 반영한다. 닫기와 뒤로가기는 초안을 취소한다. 모바일 카드의 정보 구조는 별도 설계에서 정한다.
- 표, 카드, 상세 패널은 맡은 정보에 맞춰 배치한다. 표는 행 사이의 얇은 구분선으로 비교를 돕는다. 카드와 고정 속성 영역은 표면색과 여백으로 묶는다. 옆에서 계속 참조해야 하는 속성은 넓은 화면의 본문 옆에 둘 수 있다.
- 작업 영역은 셸 위에서 한 겹으로 읽히게 한다. 배경, 작업 영역, 고정 패널은 작은 밝기 차와 경계선으로 구분한다. 시트·메뉴·대화상자처럼 기존 화면 위에 겹치는 요소에만 방향과 강도가 있는 그림자를 쓴다. 고정 카드, 표, 입력창은 평면을 기본으로 한다. 초점·선택·오류의 식별에는 테두리, 텍스트, 아이콘을 사용한다.
- 다크와 라이트에서 동일한 시각적 우선순위를 유지한다. 브랜드 색과 상태색의 쓰임을 구분하고, 색을 구분하기 어려운 환경에서도 선택과 상태를 알 수 있게 한다. 둥근 정도, 그림자 강도, 자간과 행 높이는 화면에서 역할을 비교한 결과로 정한다.

## 모션 문법

- 페이지와 패널을 전환할 때 사용자가 어디에서 왔고 어디로 돌아갈지 알 수 있게 한다. 시트는 연결된 화면 가장자리에서 들어오며, 닫으면 열었던 컨트롤로 초점을 돌린다. 애니메이션을 줄인 환경에서도 상태와 이동 경로를 이해할 수 있어야 한다.
- 버튼을 누른 순간 입력을 받았다는 신호를 준다. 저장, 공개, 데이터 갱신의 완료는 실제 작업 결과가 도착했을 때 표시한다. 오류는 필드 또는 관련 영역의 문구로 안내한다.
- 첫 로딩에 스켈레톤을 쓸 때는 최종 내용의 자리를 잡아 레이아웃 이동을 줄인다. 같은 조건의 재조회는 표시 중인 내용을 유지하면서 해당 영역의 진행 상태를 알려준다. 다른 조건의 응답을 기다리는 동안 이전 데이터를 보여준다면 그 데이터의 조건도 함께 표시한다.
- 성격을 드러내는 움직임은 반복 작업의 입력이나 읽기를 방해하지 않는 순간에 제한한다. 사용자 설정으로 모션을 줄여도 필요한 피드백은 남는다.

응원법 목록 시안은 동일 데이터와 기능에서 **Compact · Balanced · Expressive**의 타이포, 행 높이, 여백, 표면만 바꾼다. Balanced를 비교 기준으로 삼고, 첫 행의 위치, 읽히는 행 수, 긴 제목과 상태의 판독성을 다크·라이트에서 확인한다. 모션은 실제로 GA를 갱신하고 모바일 필터를 적용하거나 취소하면서 비교한다.

시그니처 후보는 공개 웹에서 팬이 응원 타이밍을 놓치지 않게 돕는 순간이다. 현재 줄 강조, 다음 응원 구간 예고, 수동 탐색 후 현재 위치 복귀를 같은 곡에서 조작해 본 뒤 채택을 결정한다. 채택한 시각·모션 규칙에는 선택 이유와 적용 범위, 예외를 기록하고, 이후 새 화면에서 같은 과업으로 일관성을 확인한다.

## 디자인을 판단하는 원칙

- **실제 과업에서 출발한다.** 화면의 대상 사용자, 사용 상황, 핵심 행동과 완료 조건을 먼저 정한다. 공개 웹의 읽기·응원 참여와 Console의 탐색·편집을 구분하고, 두 화면에 같은 정보 밀도나 마케팅 구성을 일괄 적용하지 않는다.
- **과제 적합성·완성도·개성을 함께 본다.** 요구를 충족하는지, 읽고 조작하는 데 오류가 없는지, 서비스다운 선택인지 각각 설명한다. 오류가 적다는 이유만으로 최선의 시안이라 판단하거나 개성을 이유로 읽기·조작 문제를 통과시키지 않는다.
- **기존 체계에서 발전시킨다.** 유사 화면과 기존 컴포넌트, 앱별 semantic token, 서체·간격·상태 표현을 먼저 확인한다. 새 값이나 패턴은 기존 체계로 해결되지 않는 이유와 적용 범위를 설명하고 실제 렌더에서 비교한다. 토큰의 구현 계약은 Frontend §16을 따른다.
- **콘텐츠가 구성을 결정한다.** 비교할 정보는 정렬하고, 함께 읽을 내용은 여백과 위계로 묶는다. 카드·구분선·라벨·아이콘·모션은 정보 관계나 행동을 설명할 때 사용한다. 장식을 채우려고 콘텐츠를 만들지 않는다.
- **실제 자료로 선택한다.** 등록된 제목·출처·상태 등 대표 콘텐츠와 긴 한글, 빈 결과, 오류를 사용한다. 시안용 데이터는 시안임을 표시하고 검증되지 않은 통계·후기·기능·공식성·저장 보장을 사실처럼 노출하지 않는다.
- **설명 가능한 개성을 만든다.** 공개 화면의 응원 타이밍과 콘텐츠, Console의 안정된 탐색·편집 경험에서 차이를 만든다. 레퍼런스는 어떤 문제를 푸는지 설명하며 선택하고 외형만 복제하지 않는다.

## 디자인 생성 절차

### 1. 브리프와 기준 화면 확인

생성·수정 전에 다음을 짧게 정리한다. 기존 이슈·PR·화면 명세가 있으면 링크와 변경점만 기록한다. 새로운 계획 파일을 작업마다 만들지 않는다.

- 대상 화면·사용자·사용 상황과 가장 중요한 행동
- 필요한 콘텐츠·정보 우선순위·성공 조건
- 유지해야 할 동작·권한·상태·사용자 지정 범위
- 기존 화면·관련 명세·컴포넌트·토큰·브랜드 자료
- 적용할 화면 폭·테마·입력 방식·로딩 및 실패 상태
- 확인된 사실, 설계 가정, 추가 확인이 필요한 항목

자료가 부족하면 기존 문서와 구현부터 확인하고, 진행 가능한 범위는 가정을 명시해 작업한다. 권한·공개 상태 등 계약을 임의로 만들지 않는다. 적용 여부가 확정되지 않은 기존 제안은 채택한 요구와 구분한다.

### 2. 방향 선택과 생성

새 화면이나 큰 방향 변경은 동일한 콘텐츠·기능·화면 폭에서 대안을 비교하고, 핵심 행동의 발견·판독·조작과 서비스 적합성으로 선택 이유를 설명한다. 앞 절의 Compact · Balanced · Expressive 비교는 응원법 목록에 한정한다. 모든 화면에 같은 세 시안이나 구성을 강제하지 않는다. 적용한 디자인 스킬의 시안·선택 절차가 있으면 함께 따른다.

국소 수정과 이미 선택된 시안의 구현은 해당 범위에서 기존 구성을 발전시킨다. 생성 도구·모델에는 브리프, 관련 원칙, 실제 레퍼런스와 보존 조건을 전달한다. 도구가 저장소 문맥을 알고 있다고 가정하지 않는다.

### 3. 구현과 재검수

선택한 시안과 실제 렌더를 같은 콘텐츠·화면 폭·상태에서 비교한다. 아래 검수표로 문제를 찾아 수정한 뒤 변경된 부분을 다시 확인한다. 이미지 시안의 승인과 실제 기능·접근성·성능 검증은 구분한다. 코드 검사 범위와 필수 build/browser 검증은 [Testing Architecture](migration/oioi-bwg-architecture-clean-v1/10-testing-architecture.md)와 AGENTS §8을 따른다.

## 습관적인 AI 디자인 패턴 점검

Frontier Design의 공개 연구에서 가져온 것은 아래 반복 패턴을 돌아보는 관점이다. 특정 표현을 썼다는 이유만으로 실패 처리하거나 AI가 만들었다고 판정하지 않는다. 사용자 과업에 필요한지, 같은 장치를 의미 없이 반복했는지 확인한다.

| 돌아볼 패턴 | 이 프로젝트에서 확인할 질문 |
| --- | --- |
| 모든 제목 위의 작은 대문자 라벨 | 제목에 없는 분류나 맥락을 제공하는가? 한글 화면에 불필요한 영문 장식을 추가했는가? |
| 제목 일부의 관습적인 이탤릭·색 강조 | 강조한 단어가 정보 위계상 중요한가? 가독성과 서체 표현이 자연스러운가? |
| 모든 섹션의 장식용 번호 | 실제 순서·단계·참조를 나타내는가? 의미 없는 번호로 화면을 복잡하게 했는가? |
| 모든 정보를 카드로 감싸기 | 독립된 정보나 상호작용 단위인가? 정렬·여백·구분선으로 더 잘 읽히는가? |
| 짧은 슬로건의 반복 | 무엇을 보고 어떻게 행동하는지 알 수 있는가? 실제 콘텐츠와 작동 설명을 생략했는가? |

화살표 방향 같은 모델별 버릇을 디자인 금지 규칙으로 옮기지 않는다. ‘AI처럼 보이지 않음’은 품질이나 인간 제작의 증거가 아니며, 미완성 화면도 익숙한 AI 패턴이 적을 수 있다. 독창성은 과업 적합성과 완성도를 충족한 상태에서 판단한다.

## 디자인 검수표

아래는 공개된 평가 관점을 프로젝트에 맞게 정리한 자체 검수표이며, Frontier Design의 비공개 전체 35개 항목을 재현한 것이 아니다. 합산 점수나 Slop 점수를 합격 기준으로 사용하지 않는다.

| 관점 | 확인할 내용 |
| --- | --- |
| 과제·브랜드 적합성 | 브리프의 핵심 행동과 제약을 충족하며 공개 웹·Console의 목적과 서비스 태도에 맞는가? |
| 정보 위계·배치 | 첫 시선과 읽는 순서가 과업을 돕는가? 제목·검색·필터·결과·주요 행동의 관계가 분명한가? |
| 타이포그래피 | 제목·본문·보조 정보의 역할이 구분되는가? 긴 한글·숫자·혼합 언어와 줄바꿈·말줄임이 읽히는가? |
| 색·표면·일관성 | 기존 토큰을 사용하며 테마가 달라도 위계와 상태가 유지되는가? 불필요한 중첩·그림자·장식이 없는가? |
| 이미지·아이콘 | 실제 콘텐츠에 맞으며 크롭·비율·해상도가 적절한가? 조작 아이콘의 의미와 이름을 이해할 수 있는가? |
| 콘텐츠·문구 | 실제 대상과 행동을 구체적으로 설명하는가? 말투·용어·출처·저장 및 공개 안내가 PHILOSOPHY와 계약에 맞는가? |
| 조작·상태·복구 | 주요 흐름을 끝낼 수 있는가? 로딩·빈 결과·오류·비활성·선택 상태가 구분되며 실패 후 다음 행동과 보존 여부가 정확한가? |
| 반응형 | 대표 모바일·데스크톱과 경계 폭에서 긴 내용, 확대, 시트·메뉴가 잘리거나 주요 행동을 가리지 않는가? |
| 접근성 | 키보드 순서·포커스 표시/복귀·컨트롤 이름·대비를 확인했는가? 색 외의 상태 단서와 모션 감소 대안이 있는가? |
| 모션·성능 | 움직임이 상태를 설명하며 읽기·입력·재생 추적을 방해하지 않는가? 로딩 이동과 실제 조작 중 지연을 확인했는가? |

공개 웹은 같은 곡으로 탐색·읽기·현재 응원 구간 식별을, Console은 같은 데이터로 목록 탐색·조건 적용·편집·결과 확인을 검수한다. 실제 변경과 관계있는 흐름만 선택하며 이 문서로 새 기능 구현을 요구하지 않는다.

### 근거와 판정 기록

단일 PR에서는 PR 본문에, 여러 PR이 공유하는 채택 규칙은 기존 소유 문서에 기록한다. 검수용 RESULT·점수표 파일을 매번 만들지 않는다.

- **대상과 조건:** 화면/경로, 구현 커밋 또는 시안 버전, 데이터·상태, 화면 폭·테마·입력 방식
- **관찰과 근거:** 실제로 본 스크린샷·조작 결과·측정·실행한 검사. 기대하는 동작과 관찰 사실을 구분
- **판정:** 관점별 통과 / 수정 필요 / 미확인 / 해당 없음과 이유. 문제 위치·사용자 영향·수정 방향 명시
- **수정 후 확인:** 재검수 결과, 남은 제약, 보류 항목과 완료 조건

스크린샷만으로 키보드·스크린리더·성능이나 전체 접근성 준수를 확인했다고 쓰지 않는다. 도구나 환경 문제로 확인하지 못하면 미확인으로 기록하고 시안 또는 부분 검수 상태로 보고한다. 필요한 확인이 남은 화면을 검수 완료로 선언하지 않는다.

핵심 행동 불가, 잘못된 출처·공개 상태 안내, 내용 잘림으로 인한 정보 유실, 필수 조작의 키보드 접근 불가 등은 수정 후 재검수한다. 취향 차이와 사용을 막는 오류를 구분하고, 작은 장식 선호로 기존 계약·사용성을 약화하지 않는다.

## 출처와 유지 기준

2026-11-23 사용자 요청으로 기존 디자인 철학·시각·모션 문법에 생성·검수 절차를 추가했다. 아래 공개 자료의 실무 브리프, 전문가 비교, 오류 진단, 반복 패턴 점검 관점을 채택했다. 검수표와 프로젝트 적용 판단은 자체 규칙이다.

- [Frontier Design Methodology](https://contralabs.com/frontierdesign/methodology): 실제 조건을 포함한 과제와 비교 평가
- [Frontier Design Rubric](https://contralabs.com/frontierdesign/rubric): 구조·시각적 완성도·콘텐츠와 사용성의 관점
- [Frontier Design 연구 글](https://contralabs.com/frontierdesign/blog): 기준 점수와 선호의 차이, AI 반복 패턴과 지표의 한계
- [Dataset 안내](https://contralabs.com/frontierdesign/dataset): 전체 데이터셋은 별도 요청 대상이며 공개 자료만 검토

변하는 모델 순위·점수·탐지기의 세부 구현은 프로젝트 규칙으로 고정하지 않는다. 제품 화면을 설계·리뷰하는 담당자는 사용자 결정, 채택한 규칙·예외, 관련 계약 또는 연구 근거가 바뀔 때 이 문서를 갱신하고 이유·날짜·근거를 남긴다. 외부 자료의 변경만으로 기존 결정을 자동 변경하지 않는다. 문서 위치를 바꿀 때는 AGENTS와 문서 안내의 링크를 같은 변경에서 이관한다.
