# P11 기존 관리자·사용자 화면 구조 개선

2026-11-01 사용자는 기존 화면 개선을 P11, 새 계정·권한·보안을 [P12](P12-PLAN.md)로
분리하고 문서화 및 P11의 작은 첫 작업을 지시했다. 이 문서는 여러 변경이 공유할 범위와
미정 사항을 소유한다. 현재 상태는 [WORK](../../../WORK.md), 단일 PR의 실행·검증은 PR 본문이 소유한다.

## 1. 기준과 관찰

[헌법](../../oioi-bwg-architecture-clean-v1/01-architecture-constitution.md),
[Frontend](../../oioi-bwg-architecture-clean-v1/02-frontend-architecture.md),
[Form/State](../../oioi-bwg-architecture-clean-v1/08-form-state-architecture.md),
[Testing](../../oioi-bwg-architecture-clean-v1/10-testing-architecture.md),
[Domain §8·15](../../DOMAIN_SPECIFICATION.md), [표현 기준](../../../PHILOSOPHY.md)을 따른다.

관찰 기준은 위 source의 `migration_main`이다. 초기 체크아웃은 오래된 feature 브랜치였으며
로컬 `migration_main`을 원격과 같은 SHA로 pull한 뒤 첫 작업 브랜치를 만들었다.
기존 미커밋 공개 웹 UI 제안·README 수정은 이번 변경에 포함하지 않는다. 운영 화면·DB를 재조회한 기록은 아니다.

- 곡·앨범 목록은 `packages/ui` Data Table을 사용한다. 열 조절·페이지 전체 선택 부품은 있지만
  Console 소비처는 정렬·페이지 이동만 등록했다.
- 곡 목록은 개별 선택·파형 작업 파일 다운로드와 검색/페이지 변경 후 선택 유지를 제공한다.
- 알림함은 단건 읽음·모두 읽음·이전 내역 조회·브라우저 push 설정을 제공한다. 현재 종류는 파형 성공/실패다.
- 공개 응원법은 재생·seek·강조·자동 스크롤·공연 모드 선택과 guide URL 연결을 제공한다.

## 2. 확정 범위와 미정 사항

| 영역         | 요청한 방향                                                                     | 구현 전 남은 결정                                            |
| ------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 곡 추가·수정 | 넓은 편집 화면과 목록에서 1 depth                                               | 하위 페이지 또는 URL 연결 오버레이, 미저장 입력·목록 복귀    |
| 곡 열·필터   | YouTube ID, 공식, 사용자 노출, waveform, 콘서트, 페스티벌 표시 및 5개 상태 필터 | 아래 판정 단위, 같은 필터 내 다중 값 규칙                    |
| 선택         | 모두 선택 제공                                                                  | 현재 페이지/필터 결과 전체, 필터 변경 시 선택·일괄 작업 범위 |
| 알림 내역    | 테이블·필터                                                                     | 읽음/종류/기간 등 채택할 필터, 선택 읽음 필요성              |
| 공통 테이블  | 테이블 사용 화면에 열 너비 조절                                                 | 화면별 최소 너비·모바일 동작·설정 유지 범위                  |
| 공개 응원법  | 기존 동작을 보존하며 UI/UX 개선                                                 | 최신 화면에서 실제 불편 확인 후 범위 확정                    |

여러 필터의 동시 적용은 확정 요구다. 구체 연산은 제안과 확정을 구분하며 전체 구현 순서나 PR 분할을
아직 확정하지 않는다. YouTube ID 표시는 내부 UUID identity 변경이 아니다.

- 공식은 모드별 공개 snapshot의 `OFFICIAL/FANDOM` 출처다. 기존 관리자 `hasOfficialCheer`와
  공개 화면의 출처 판정이 다를 수 있으므로 새 필터의 권위로 legacy flag를 그대로 쓰지 않는다.
- 노출은 Song 설정, Album 설정, guide 공개 상태를 구분한다. 단일 열이 설정값인지 실제 노출인지 미정이다.
- 콘서트/페스티벌은 Song+mode별 guide다. 등록과 현재 공개를 구분하며 없음·비공개를 임의로 합치지 않는다.
- waveform은 데이터 존재와 현재 YouTube source에 맞는 유효 결과를 구분한다.
- 알림함을 여는 것만으로 읽음 처리하지 않는 기존 계약을 유지한다.

## 3. 첫 구현 단위: 곡·앨범 목록 열 너비 조절

승인된 오늘 범위는 기존 두 목록의 작은 확장이다. 공용 Data Table의 공식 sizing/resizing 기능과
기존 드래그·터치·좌우 방향키 부품을 활용한다. 도메인 API·권한·DB·P09 편집 도구는 변경하지 않는다.

첫 버전의 구현 선택:

- 열별 초기·최소 너비를 앱에서 지정하고 작은 화면은 테이블 영역 안에서 가로 스크롤한다.
- 기존 breakpoint별 숨김 열을 유지하되 숨긴 열을 전체 너비에 합산하지 않는다.
- 너비는 마운트된 목록의 표시 상태로만 유지한다. 새로고침/재진입 시 초기화하고 URL·계정·브라우저에 저장하지 않는다.
  장기 유지 방식은 후속 결정이며 이 선택을 전체 P11의 확정 정책으로 확대하지 않는다.
- 정렬·페이지 이동·곡 선택·편집/삭제 진입과 읽기 권한의 기존 동작을 보존한다.

검증은 저장소 기본 명령과 실제 소비 컴포넌트의 브라우저 fixture로 수행한다.
마우스·키보드·터치, 최소 너비, breakpoint 전환, 표 내부 스크롤과 문서 overflow를 확인한다.
fixture는 실제 DB·인증·운영 수용 검증과 구분하고 결과·화면 근거를 PR에 남긴다.

## 4. 추가 합의: 공용 뱃지 팔레트

2026-11-02 사용자는 기존 Console 디자인을 유지한 뱃지 시안을 승인하고 적용을 지시했다.
새 색상 값을 추가하지 않고 Console CSS의 `--qwer-q/w/e/r`, `--qwer-bwg`,
`--qwer-rockation`, `--muted`, `--border`, `--foreground`, `--destructive`를 재사용한다.
색상은 작은 점과 옅은 배경·테두리로 구분하고 글자는 동일한 기본 텍스트 색으로 표시한다.
기존 공용 Badge의 크기·형태·focus·asChild API는 유지한다.

Console 모드별 출처의 합의한 표현은 `official`(Q 화이트) / `fan-made`(바위게 블루)이며,
응원법 한 열에서 콘서트 / 페스티벌 순서로 두 출처를 표시하고 미등록은 뱃지 없는 `-`로 둔다.
이는 Console 시안의 표현 합의이며 공개 사용자 화면의 공식 / 팬덤 용어를 일괄 대체하지 않는다.

이번 팔레트 적용 단위는 공용 Badge와 기존 곡 목록 뱃지의 외형까지다. 현재 관리자 목록 DTO는
모드별 출처를 제공하지 않으므로 legacy `hasOfficialCheer`의 false를 팬덤으로 해석하지 않는다.
기존 목록의 표시 조건·문구는 보존하며, 모드별 출처 열·등록/공개 판정·필터 연결은 §2의 후속이다.
팔레트의 브랜드 색에 권한·승인·성공 같은 새 도메인 의미를 부여하지 않는다.

## 5. 추가 합의: 목록 표시 개수

2026-11-02 사용자는 몇 개씩 볼지 선택하는 페이지네이션과 기본값 10개를 요청했다.
현재 테이블 소비처인 곡·앨범 목록에 공용 `DataTable.Pagination`의 `pageSizes`를 연결한다.
첫 적용의 선택지는 10·20·50개로 구성하며, 이는 표시 개수의 UI 선택이고 서버 조회 한도를 뜻하지 않는다.
기존 공용 동작대로 개수 변경 시 첫 페이지로 이동한다. 정렬·검색·곡 선택은 보존하며,
별도 URL·계정·브라우저 저장 기능은 이번 단위에 추가하지 않는다.

## 6. 화면·진입 합의와 후속 구현 단위

2026-11-02 사용자는 아래 논의를 정리한 뒤 단계별 구현을 지시했다. 초기 §2의 미정 사항 중
아래 항목은 이 합의로 구체화하며, 목록의 세부 열·필터 판정과 모두 선택 범위는 계속 미정이다.

- 내부 `Song/song`은 유지한다. 화면을 트랙으로 바꿀지는 검토 사항이며 당장은 곡 명칭을 사용한다.
- 곡 정보의 기본 진입은 조회 전용이다. 편집으로 전환하면 제목은 **곡 정보 수정**이며,
  곡 추가도 같은 정보 구조를 사용한다. 목록 제목은 정보 조회, 연필은 정보 수정 진입을 목표로 한다.
- 미저장 변경의 취소·앱 내 이탈은 확인 오버레이로 처리하고 중복 제출을 방어한다.
  새로고침·탭 닫기는 브라우저 기본 확인창의 지원 한계를 구분한다. 실패·충돌·재인증 시 초안을 보존한다.
- UI는 표시·이벤트, model hook은 편집 세션·mutation·캐시·재인증 조합, 순수 함수는 변환·계산을 맡는다.
  Query 서버 상태와 RHF 초안의 소유권을 유지한다. 디자인은 Console `globals.css`와 기존 Radix 부품을 따른다.
- 응원법 관리는 별도 메뉴로 두고 목록 한 행은 곡+모드의 Guide 하나로 구성한다.
  기존 P09 도구를 재사용하면서 대상 guide를 정확히 연결한다. 편집 도구 자체 확장은 제외한다.
- 응원법 추가는 곡 정보 수정과 응원법 목록에서 같은 화면으로 진입한다. 곡 정보 진입에서는 곡을 미리 선택한다.
  곡은 검색형 Combobox, 모드는 콘서트/페스티벌, 출처는 official/fan-made로 선택한다.
  공식 원본 링크는 필수이고 팬덤 원본·안내 영상 링크·설명은 선택이다. LRC는 다시 받지 않고 곡의 가사를 사용한다.
- 공개 여부는 기존 PUBLISH/UNPUBLISH 기반을 활용한다. 초기 비공개는 권장안이며 공개 권한·승인은 P12와 연결한다.
  버전 목록·비교·복원 UI는 제외하되 기존 불변 snapshot·공개 이력·충돌 방지는 보존한다.

구현은 관심사와 선행 계약을 기준으로 진행한다. 현재 정보 화면에 필요한 관리자 UUID 상세 조회가 없으므로
첫 checkpoint는 비공개 곡·null slug도 조회하는 관리자 DTO·서비스·GET 경계다. 공개 조회와 분리하고
응원법 등록, 현재 공개 조치, 출처를 구분하며 private row·내용 이력을 노출하지 않는다.
다음 단위에서 이 조회를 실제 정보 페이지와 조회/편집/추가 세션에 연결한다. 이후 모드별 응원법 목록·진입,
추가·편집을 순차 연결하되 각 PR은 독립 검증 가능한 범위로 나눈다. 새 공개 조작은 P12 정책과 대조한다.
실행·검증은 각 PR 본문에 남기며 이 조회 checkpoint만으로 화면 전환이나 P11 완료를 선언하지 않는다.

2026-11-02 화면 연결 구현 선택: `/admin/songs/{UUID}`는 조회, `?edit=true`는 수정,
`/admin/songs/new`는 추가로 사용한다. URL을 모드의 유일한 소유자로 두며 RSC가 판정하고 별도 client mode를 저장하지 않는다.
편집·추가 진입은 문서 탐색으로 유지해 브라우저 뒤로가기에도 `beforeunload`를 적용한다.
앱 링크·취소·알림 결과 이동은 Radix 확인 오버레이, 브라우저 뒤로가기·새로고침·탭 닫기는 기본 확인창을 사용한다.
알림의 코드 기반 이동은 현재 폼의 확인 콜백에 위임하며, 읽음 처리 성공 후 이동하는 기존 순서를 유지한다.
이는 전역 라우터 차단 로직을 도입하지 않는 대신 해당 진입에서 문서를 다시 읽는 선택이며,
모바일 종료 등 브라우저가 확인 이벤트를 생략하는 상황까지 보호한다고 보장하지 않는다.
저장 성공은 편집 URL을 정보 URL로 대체하고, 실패·충돌·재인증·권한 회수는 편집 세션을 유지한다.
모드별 응원법 등록·최근 공개 조치·출처는 조회로 표시하고 기존 P09 편집기로 명시적으로 연결한다.
모드별 응원법 관리 화면과 새 공개 조작은 후속이며 이번 곡 정보 전환의 완료 조건과 구분한다.

2026-11-02 다음 checkpoint는 관리자 응원법 목록의 계약·조회 경계와 실제 목록 화면이다.
Guide별 행으로 조회하고 공개 이력 없음과 공개 중단을 구분한다. 공개 조치는 실제 사용자 노출 판정이 아니다.
기존 P09 경로는 지정 legacy writer 하나만 저장하므로 모든 Guide를 곡 slug로 연결하지 않는다.
현재 writer 대상·공개 조치·기준 영상·slug 조건이 맞는 행만 기존 편집 진입을 제공하고,
진입 시 요청 Guide ID와 실제 writer 대상을 다시 대조한다. 이는 기존 호환 경로의 안전한 연결이며
모드별 생성·편집 또는 새 공개 정책의 구현 완료를 뜻하지 않는다. 버전 관리 UI는 계속 제외한다.

2026-11-02 목록 화면 연결: `/admin/cheer-guides`에서 검색·모드·출처·공개 조치를 AND로 적용한다.
공용 표의 열 조절·정렬·10/20/50개 표시(기본 10)를 사용한다. 사용자 너비 피드백에 따라
이 목록은 `fillWidth`로 본문 너비를 채우고 모바일에서는 최소 표 너비와 내부 가로 스크롤을 유지한다.
공용 표의 기본 너비 선택은 보존하며 다른 목록의 너비를 일괄 변경하지 않는다.
기존 편집 진입은 Guide ID를 대조하고 저장 성공 후 응원법 목록 cache를 무효화한다.
모드별 추가·독립 편집과 새로운 공개 조작은 후속으로 유지한다.

## 7. 경계와 완료 조건

P12의 초대·승인·재인증·감사는 이번 UI 확장에 섞지 않는다. 독립 설정 페이지의 필요성은 미정이다.
P09는 실제 사용 중 필요가 생길 때 개선하며 P10 Grid/Snap·BPM·타격 구간 선택을 가져오지 않는다.
공개 응원법 UX는 관리자 편집기 개선과 별도 관심사로 다룬다.

채택한 화면별 요구의 완료 조건과 검증을 합의하고, 구현·사용자 수용을 구분해 닫는다.
단일 열 조절 PR이 끝나도 P11 전체 완료로 판정하지 않는다. 여러 PR의 상세 기록을 이 문서에 복제하지 않는다.
P11 담당자는 범위 결정 때 이 계획을 갱신하고, 종료 시 유효 계약은 active 문서, 실행 요약은 단계 최종 결과로
회수한 뒤 이 계획의 유지·통합을 판단한다. 관련 없는 과거 문서 정리는 수행하지 않는다.

2026-11-02 후속 사용자 피드백: 곡·앨범·응원법 목록은 같은 Console 표 컴포넌트에서 너비·여백을 정한다.
열 정렬은 공용 `meta.align`으로 헤더·본문에 함께 적용하고 정렬 버튼 여백이 제목 위치를 밀지 않게 한다.
응원법에 Guide ID별 행 선택을 추가한다. 검색·페이지 변경에도 개별 선택을 유지하며, 필터 전체 자동 선택은 추가하지 않는다.
사용자는 이력 없는 응원법만 실제 삭제하는 기준을 선택했다. 내용 snapshot 또는 공개 조치가 있는 Guide는 삭제하지 않는다.
정렬·선택 기반을 먼저 검증하고 이어서 이 조건을 서버와 삭제 UI에 연결한다.

2026-11-02 삭제 API 연결: [Domain §8.0](../../DOMAIN_SPECIFICATION.md#80-p07-데이터와-공개-조회)의 이력 없는 Guide 삭제 기준을 조건부 DELETE와 기존 FK로 확인한다. 목록은 삭제 가능 여부만 제공하며 내용·이력을 내려주지 않는다. 개별·선택 삭제 확인 UI는 다음 연결 범위다.
