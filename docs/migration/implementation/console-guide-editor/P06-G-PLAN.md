# P06-G 관리자 계정 관리 계획

사용자는 F 이후 G 단계에서 관리자 페이지에 계정 관리 기능을 추가하고, 지금은 계획만 작성하도록 요청했다.
**F의 운영 전환 완료 뒤 시작하는 후속 기능**이다. 기존 D·E·F 완료 조건을 바꾸거나 G로 넘기지 않는다.
이 문서는 설계 제안이며 신규 계정 생성·공개 MFA 등록·DB migration·배포를 승인하거나 실행한 기록이 아니다.
아래 새 정책은 G0에서 Domain/active architecture에 반영하기 전까지 구현 기준으로 사용하지 않는다.

## 2026-10-23 통합 개정 — Web 인증 종료 반영

최초 제안은 `9beb8fcb90e8d1408e5b7c961e8cff940d109d3b`의 관찰로 보존한다.
현재 통합 기준 `ef0e1224fa7f289bfde0cba60dfbbab9e58cf42f`에는 E3의 Web 인증 종료가 반영됐다.
헌법 §5·Auth §4.0·Domain AUTH-001과 [E3 결과](P06-E3-RESULT.md)를 우선한다.

- 아래 §2의 Web request context 관찰은 최초 소스의 역사 기록이다. 현재 Web에는 해당 adapter·세션이 없다.
- §3.2·§4·G2b/G4·§6의 Web 전체 세션 회수 전제는 폐기한다. G의 세션 회수는 Console을 대상으로
  설계하며, Web의 공개 조회·인증 endpoint/과거 cookie 비사용 검증은 기존 종료 경계를 유지하는 회귀다.
- G 구현을 위해 Web 로그인·인증 adapter·메일 consumer를 복구하지 않는다. 계정·초대·Console MFA와
  회수 정책은 G0에서 active 계약을 개정한 뒤 구현한다. 현재 계정/키를 변경하지 않는다.
- F 운영 전환은 여전히 보류이고 G는 F 완료 뒤의 후속 기능이다. 이 통합은 계획 승인·문서 충돌 해소이며
  F 전환·G 구현·메일 발송·배포 완료를 뜻하지 않는다.

## 1. 목표와 범위

목표는 Console에서 계정을 조회·관리하고, 초대받은 관리자가 **SSH 없이 회사·집의 HTTPS 브라우저와
인증 앱으로 사용을 시작**하게 하는 것이다. 운영자가 비밀번호나 OTP를 대신 받아 입력하지 않는다.

| 포함           | 첫 버전의 사용자 동작                                                                       |
| -------------- | ------------------------------------------------------------------------------------------- |
| 계정 목록·상세 | 기존 계정의 이메일·닉네임·역할·활성 상태·MFA 등록 여부 조회, 검색·필터·페이지 이동          |
| 관리자 초대    | 이메일 초대 발송·재발송·취소, 미수락/만료/완료 상태와 발송 실패 확인                        |
| 초대 수락      | 본인 이메일 확인, 신규 계정의 비밀번호·닉네임 설정 또는 기존 계정 본인 인증, HTTPS MFA 등록 |
| 권한·상태 관리 | 기존 USER/REVIEWER/ADMIN 역할 변경, 정지·복귀, 변경 사유와 영향 확인                        |
| 계정 보안      | 비밀번호 재설정 안내, 본인의 인증기 교체·복구 코드, 다른 관리자에 의한 제한된 복구 지원     |
| 변경 이력      | 수행자·대상·작업·사유·시각·결과 조회, 인증 비밀값은 기록하지 않음                           |

공개 일반 회원가입 재개, 새 OWNER/SUPER_ADMIN 역할, 세부 권한 편집기, 대량 작업·CSV,
계정 병합·강제 삭제, 타인의 비밀번호/이메일 직접 덮어쓰기, 기기별 세션 목록, Passkey/SSO는 제외한다.
기존 계정의 개인정보·콘텐츠 생명주기는 보존한다. 영구 삭제는 별도 도메인 설계로 남긴다.
최초 운영자와 모든 관리자가 잠긴 경우의 비상 복구에는 D의 보호된 CLI를 유지한다.

## 3. 사용자 흐름 제안

### 3.1. 초대부터 관리자 사용 시작까지

1. MFA를 통과한 ACTIVE ADMIN이 계정 관리에서 이메일을 지정하고 최근 재인증 후 초대를 보낸다.
   받는 사람이 설정할 비밀번호·OTP를 운영자가 지정하거나 조회하지 않는다.
2. 받는 사람은 canonical Console HTTPS의 이메일 초대 링크를 연다. GET은 상태를 변경하거나
   초대를 소모하지 않는다. 보안 메일 스캐너의 링크 방문만으로 초대가 끝나지 않게 한다.
3. 신규 이메일은 소유 확인 후 비밀번호·닉네임을 설정한다. 기존 계정이면 기존 비밀번호로 본인 인증하며
   새 Account 생성·기존 비밀번호 변경·이메일만 일치하는 자동 연결을 하지 않는다.
4. 초대 대상과 목적에 묶인 제한된 등록 권한으로 QR을 표시하고 인증 앱의 코드를 확인한다.
   등록 전 권한은 관리 API·일반 Console 세션으로 사용할 수 없다.
5. 초대 유효성·초대자 현재 권한·대상 상태를 다시 확인한 뒤 관리자 권한 부여, MFA 활성화,
   관련 version 증가와 초대 완료를 하나의 service transaction에서 확정한다.
6. 완료 화면에서 일반 로그인으로 이동한다. 등록 증명을 자동으로 관리 세션으로 승격하지 않는다.

신규 계정의 등록 중 상태는 기존 `PENDING_VERIFICATION` 활용을 제안하되 의미·만료 정리는 G0에서 확정한다.
MFA가 필요한 ADMIN 권한은 최종 확인 전 부여하지 않는 안이다. 현재 AUTH-009의 ACTIVE ADMIN 전제와
충돌하므로, 초대에 한정된 등록 권한을 먼저 명세한다. 기존 USER/REVIEWER는 수락 중 기존 상태를 유지한다.
이미 MFA가 활성인 관리자에게 초대 링크로 secret을 교체하지 않는다. 정지·삭제 계정도 초대로 부활시키지 않는다.
등록 중 포기·만료·재발송은 기존 계정과 활성 MFA에 영향을 주지 않아야 한다.

초대 생성/재발송은 동일 이메일의 유효 초대를 중복 생성하지 않으며 이전 링크는 무효화한다.
초대자가 강등·정지되면 미완료 초대 권한도 회수하고 복귀·재승격으로 과거 초대가 살아나지 않게 한다.
초대는 대상 이메일·예정 역할·초대자·용도에 묶인 일회용 난수와 만료를 사용하고 서버에는 검증용 hash를 저장한다.
메일 전송은 DB transaction 밖에서 수행한다. 발송 실패를 성공으로 표시하지 않으며
재발송 때 새 Account나 중복 초대를 만들지 않는 최소 재시도 계약을 둔다.

### 3.2. 역할 변경·정지·복귀

- 계정 상세에서 현재 값과 변경 후 값, 회수되는 접근 범위를 보여주고 사유를 받는다.
- ADMIN 부여는 MFA 준비까지 완료되는 초대/승격 흐름으로 연결한다. 역할 드롭다운만 바꿔 미등록 관리자 사용을 허용하지 않는다.
- 자기 자신 강등·정지와 마지막 사용 가능한 관리자 제거는 기본 UI/API에서 거절하는 안이다.
  사용 가능 조건은 ACTIVE·ADMIN·활성 MFA로 정의하며 동시 변경에도 최소 한 명이 유지돼야 한다.
- 대상 상태/version이 화면 확인 후 바뀌면 충돌로 종료하고 새 값을 보여준다. 자동으로 덮어쓰지 않는다.
- 정지·비밀번호 재설정은 Web과 Console의 기존 세션을 회수한다. 복귀·재승격으로 옛 세션이 되살아나지 않는다.
  역할 변경은 DB 인가에 즉시 반영하고 Console version도 증가시킨다.
- 위 효과를 구현·검증하기 전에는 해당 변경 버튼/API를 공개하지 않는다.

### 3.3. MFA 교체와 분실 복구

| 상황                                    | 제안하는 흐름                                                                                                |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 기존 인증기 사용 가능                   | 본인 비밀번호·기존 MFA 재확인 → 새 인증기 등록 확인 → 원자적으로 교체·version 증가 → 재로그인                |
| 인증기 분실, 복구 코드 보유             | 비밀번호·일회용 복구 코드 검증 → 제한된 HTTPS 재등록 → 새 MFA 확인 → 기존 세션/남은 복구 코드 회수           |
| 복구 코드도 없음, 다른 관리자 사용 가능 | 별도 본인확인 후 다른 관리자가 재인증·사유 입력으로 복구 승인 → 대상 비밀번호·일회용 복구 링크 확인 → 재등록 |
| 유일한 관리자 또는 모든 관리자 잠김     | D의 보호된 CLI·운영자 본인확인 절차 유지. 일반 공개 endpoint로 관리자 생성/인증 우회 금지                    |

다른 관리자의 복구 승인은 이메일 소유만으로 대신하지 않는다. 구체적인 본인확인 방법을 G0에서
정하지 못하면 해당 지원 기능은 닫힌 채로 두며, 일반 교체와 복구 코드 방식은 독립적으로 구현한다.
복구 요청·이메일 발송만으로 활성 MFA를 지우지 않는다. 검증된 복구 시작과 명시적 사고 대응 정지를 구분한다.
정상 교체는 새 코드 확인 전 기존 인증기를 보존한다. 분실 복구는 본인확인 후 이전 접근을 회수하고 재등록 권한만 준다.
재등록 실패·만료에도 password-only 관리 로그인을 허용하지 않는다.
비밀번호 재설정은 MFA 초기화를 겸하지 않는다. 비밀번호와 MFA를 모두 잃은 경우도 이메일 링크만으로
관리 권한을 발급하지 않고 위 복구 수단 또는 운영자 절차를 사용한다.

복구 코드는 등록 완료 때 본인에게 한 번 보여주고 서버에는 검증용 hash만 저장한다.
동시 사용은 한 번만 성공해야 하며 재발급/사용/교체와 회수 규칙을 명세한다. QR·secret·OTP·복구 코드 원문은
감사 이력·Sentry·분석 이벤트·브라우저 영속 저장소에 남기지 않는다. 보안 변경은 대상자에게 별도 알림을 보낸다.
관리자가 다른 사람의 활성 QR이나 복구 코드를 조회하는 기능은 제공하지 않는다.

### 3.4. 화면 구성과 오류 처리

Console 메뉴의 `계정 관리` 아래 목록·상세·초대 상태를 둔다. 목록에는 이메일/닉네임 검색,
역할·상태 필터와 페이지 이동을 제공한다. 상세는 기본 정보, 접근 권한, 보안 상태, 변경 이력으로 구분한다.
본인의 인증기 교체·복구 코드 관리는 `내 계정 보안`으로 연결한다.

- 일반 계정 상태, 초대 진행 상태, 메일 전송 결과를 같은 badge로 섞지 않는다.
- 성공 응답 전에는 변경 성공을 표시하지 않는다. 위험한 변경에 optimistic update를 쓰지 않는다.
- 입력 시작·focus만으로 오류를 표시하지 않는다. 제출/적절한 blur 검증과 필드별 복구 안내를 제공한다.
- 만료·이미 사용한 링크는 재발송 안내, 권한 변경은 현재 권한 안내, rate limit은 재시도 가능 시각을 표시한다.
- OTP 재사용 거절과 정상 유효시간을 구분한다. 등록 직후 이미 소모한 코드를 로그인에 다시 요구하면서
  일반적인 인증 실패로 표시하지 않는다. 같은 값을 재검증하지 않는 최근 인증 증명과 사용자 안내를 G0에서 정한다.
- 모바일에서도 링크 확인·QR 대신 수동 등록 정보 확인·코드 입력이 가능해야 한다.
  본인 등록에 필요한 secret 표시만 제한적으로 허용하며 목록·감사·관리자 화면에는 노출하지 않는다.

## 4. 구현 경계와 보안 설계

- 화면은 `apps/console`의 route-private UI/model에서 시작한다. Query → ky → Route Handler →
  service → repository 흐름을 유지하고 DTO/Zod는 `packages/contracts`에 둔다.
- Console guard와 service의 호출자 인가를 모두 적용한다. 현재 CLI 전용 함수를 Route Handler가
  직접 호출하는 것으로 끝내지 않는다. 공통 DB 변경 규칙은 유지하되 신뢰 경계가 다른 진입점을 구분한다.
- 계정 관리 HTTP service는 수행자·대상·작업·최근 인증·예상 version을 검증한다.
  단순 `manage all`만으로 자기 강등·마지막 관리자·초대 상태 규칙을 생략하지 않는다.
- 초대/복구 권한은 관리 JWT와 다른 제한된 목적이다. 대상/작업/기한과 서버측 소모 상태를 확인하고
  다른 계정·다른 작업·다른 origin·과거 version에서 사용할 수 없게 한다.
- 기존 전역 enrollment flag를 true로 바꿔 해결하지 않는다. 새 HTTPS 경로는 목적별 증명이 필요하며
  비밀번호만 아는 임의 ADMIN에게 등록을 열지 않는다. 기존 비공개 등록 경로는 별도로 닫힘을 유지한다.
- Web 전체 세션 회수는 최소 로그인 세대/version 비교 방식을 G0에서 검토한다. Console MFA version과
  역할을 혼동하지 않고, 두 앱에서 오래된 로그인 증명을 거절한다. 기존 JWT 처리와 배포 호환성도 명세한다.
  이는 현재 Auth §29의 미구현 보류를 개정할 실제 요구이며 기기별 세션 관리 플랫폼으로 확대하지 않는다.
- 최근 재인증은 비밀번호와 기존 MFA/허용된 복구 수단을 검증한 짧은 증명으로 처리한다.
  client가 보낸 시각·session.update를 신뢰하지 않는다. 증명 범위·소모·TTL과 TOTP replay 규칙을 함께 검증한다.
- 마지막 관리자 보호는 단순 count 후 별도 update로 구현하지 않는다. 공통 직렬화/locking 전략을
  실제 PostgreSQL에서 검증하고 CLI를 포함한 관련 변경 경로에도 적용한다. 비상 예외는 운영 절차로 명시한다.
- 권한/상태 변경·version 증가·초대 소모·감사 성공 기록의 atomic 범위를 service가 소유한다.
  이메일·QR 생성·비싼 password hashing은 lock 밖에서 수행한다.
- 인증/초대/복구 페이지와 응답은 no-store이며 CDN cache bypass, HTTPS·Origin/CSRF·host-only cookie를 유지한다.
  token은 referrer·access log·Sentry·분석에 유출되지 않도록 전달 방식을 설계하고 canonical origin에서만 링크를 만든다.
- 이메일/계정과 신뢰한 IP 기준 제한·재발송 cooldown을 둔다. 프록시 헤더 위조로 제한을 회피할 수 없어야 한다.
  계정 존재를 unauthenticated 응답으로 노출하지 않는다. 메일 발송 권한·sender는 실제 기존 설정을 확인해 재사용한다.
- CF 확인 화면이 초대/복구 POST·관리 API 응답에 끼지 않도록 배포 때 확인한다.
  고정 공인 IP·회사 네트워크 변경·별도 VPN을 일반 등록의 전제로 두지 않는다.

## 6. 검증과 완료 기준

이번 계획 PR은 Markdown 내용·상대 링크·diff만 확인한다. 앱 build·unit·관리자 브라우저 E2E는 실행하지 않는다.
구현 PR에는 저장소 기본 검증과 변경 범위에 맞는 service/API·실제 로컬 PostgreSQL 검증을 적용한다.
사용자가 제외한 관리자 브라우저 E2E를 필수 CI나 단계별 승인 절차로 다시 추가하지 않는다.
새 UI의 입력·오류·focus는 component 검사로 확인하고, 배포 시 실제 브라우저·인증 앱 수락 확인은
자동 E2E와 구분해 한 번의 명시적인 사용자 확인으로 묶는다. 계획 작성 중에는 사용자 입력을 요구하지 않는다.

핵심 자동 검증은 다음과 같다.

- guest/USER/REVIEWER/Web cookie로 관리 read/write 거절, 다른 대상/용도 token·변조된 요청 거절.
- 초대 만료·취소·재발송·메일 실패·동시 수락, 기존 이메일 중복, 정지/삭제 계정의 우회 복귀 거절.
- MFA 확인 전 관리 권한 없음, QR/복구 코드 재조회·replay 거절, 교체 실패 후 기존 factor 상태 보존.
- 동시 강등·정지에도 마지막 사용 가능한 관리자 보호, stale expected state 충돌, 감사 실패 시 변경 일관성.
- 비밀번호 재설정·정지 후 Web/Console 옛 JWT 거절, 복귀·재승격으로 과거 세션 부활 없음.
- HTTPS 쿠키/Origin·no-store·rate limit·로그 비밀 미노출, 기존 Web 공개 가입/관리 차단 유지.
- 배포/rollback이 이미 회수한 세션·MFA·초대 권한을 되살리지 않음. G 이전 이미지의 새 회수 규칙 호환성 확인.

G 완료는 계정 목록이 표시되는 것만으로 판정하지 않는다. 초대→등록→로그인과
권한 변경→회수, 인증기 교체/분실→재등록을 구분해 결과·미완료를 기록한다.
코드 병합·배포·실사용 확인도 각각 기록하며 실제 확인되지 않은 시나리오는 미실시로 남긴다.

## 7. G0에서 확정할 제안값과 남은 결정

| 결정           | 현재 제안 / 확인할 점                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------- |
| 관리 대상·주체 | 목록은 기존 계정 전체, 초대 생성은 ADMIN만. 새 역할 없이 운영하며 본인 강등·정지는 기본 금지                  |
| 초대 기한      | 24시간 초안. 재발송은 이전 증명 무효화. 새 계정의 등록 대기 보존·만료 정리 기간 함께 확정                     |
| 최근 재인증    | 5분 이내 초안. 대상/작업에 묶고 로그인·등록에서 소비한 TOTP를 불필요하게 다시 제출시키지 않음                 |
| 복구 권한      | 일회용·짧은 기한. 비밀번호 reset은 기존 AUTH-004의 15분 계약 유지, MFA 복구 기한은 별도 확정                  |
| 복구 본인확인  | 복구 코드 우선. 타 관리자 지원의 확인 근거·통지·오용 대응을 확정하기 전 해당 기능 비공개                      |
| 감사·개인정보  | 최소 필드·관리자 열람 범위·보존 기간 확정. 전체 이메일/개인정보를 자유형 사유·로그에 중복 저장하지 않음       |
| 배포·복구      | 새 schema는 기존 코드와 공존 가능하게 추가. 회수 규칙을 모르는 구버전으로 rollback할 때 유지할 차단 경계 결정 |

이 값들은 사용자에게 매번 확인을 요구하기 위한 목록이 아니라 구현 전에 합의할 정책 초안이다.
현재 계정/secret은 재생성하지 않으며 DB 상태·메일 실제 발송 가능 여부는 G 착수 시 승인된 환경에서 대조한다.

## 8. 외부 근거와 적용 한계

2026-10-21 OWASP 원문을 확인했다. 아래는 인증 안전 원칙의 근거이며 이 프로젝트의 역할·TTL·화면 구성을
OWASP가 정했다고 해석하지 않는다. 구체적인 초대/복구 흐름은 위 저장소 계약 개정 제안이다.

- [MFA 변경·복구](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html#changing-mfa-factors):
  활성 세션만 믿지 않고 기존 factor 재확인, 대체 복구 수단과 별도 통지를 고려한다.
- [Password reset token](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html#url-tokens):
  충분한 난수·보호된 저장·일회용·만료·HTTPS 원칙을 초대/복구 증명에도 적용하는 제안이다.
- [요청별 인가](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#validate-the-permissions-on-every-request):
  화면에서 버튼을 숨기는 것과 별도로 서버에서 모든 요청의 권한을 확인한다.
