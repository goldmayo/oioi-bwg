# P12 관리자 계정·권한·보안 체계

2026-11-01 사용자 결정에 따라 기존 화면 개선은 [P11](P11-PLAN.md), 새 계정·권한·보안은 P12로
분리한다. 이 문서는 여러 PR에 걸칠 요구·미정 정책·의존성과 완료 조건을 소유한다.
현재 상태는 [WORK](../../../WORK.md), 개별 실행·검증은 PR 본문이 소유한다.

## 1. 권위와 기존 계획의 관계

[헌법](../../oioi-bwg-architecture-clean-v1/01-architecture-constitution.md),
[Auth](../../oioi-bwg-architecture-clean-v1/04-auth-authz-architecture.md),
[Domain AUTH·§18·19](../../DOMAIN_SPECIFICATION.md), [Form/State](../../oioi-bwg-architecture-clean-v1/08-form-state-architecture.md),
[표현 기준](../../../PHILOSOPHY.md)을 상위 기준으로 따른다.

**아래 확정은 사용자 요구의 확정이며 active 계약 개정·구현 완료가 아니다.** 현재는 단일 ADMIN과
`manage all`, 비밀번호+TOTP, ACTIVE·MFA version 재검사를 사용한다. 공개 Web에는 로그인 기능이 없다.
P12 구현 전에 영향을 받는 Domain/Auth 계약을 같은 변경 단위에서 먼저 개정해야 한다.

[P06-G](P06-G-PLAN.md)는 초대·HTTPS MFA·회수·복구의 기존 미구현 제안과 고정 근거다.
새 super 역할 제외·모든 ADMIN의 계정 관리 전제는 아래 사용자 결정에 맞춰 재검토한다.
과거 계획을 결과에 맞춰 고치거나 새 정책과 병렬 소유하지 않고, 이후 상세 결정은 이 문서에서 관리한다.
기존 Web 회수 전제는 G의 2026-10-23 정정대로 복구하지 않는다.

## 2. 확정한 사용자 요구

- 새로 만들 `oioibwg@gmail.com` 계정을 슈퍼관리자로, 기존 개인 계정을 일반 관리자로 운영한다.
  이메일 주소를 권한 식별자로 하드코딩하지 않는다. 실제 계정 생성·전환은 별도 실행 범위다.
- 일반 관리자는 콘텐츠 운영, 슈퍼는 관리자 초대·권한 변경·회수도 담당한다. 삭제·훼손 방지 정책을 설계한다.
- 일반 관리자의 콘텐츠 수정은 슈퍼관리자 승인 후 공개한다.
- 초대 자체가 가입 사전 승인이다. 이메일 소유 확인·MFA 등록 완료 후 활성화하며 별도 최종 승인은 두지 않는다.
- RBAC+ABAC 기반 권한 매트릭스, 관리자 목록·상세·추가·편집·이메일 초대 가입을 제공한다.
- 관리자 행동 로그를 수집하고 감사 페이지는 슈퍼관리자만 접근한다.
- 개인정보 마스킹을 KISA 개발보안 자료·개인정보 보호 법령에 근거해 설계한다.
- My 진입 시 현재 비밀번호로 재인증하며 내 정보·비밀번호·알림 수신 설정을 제공한다.

Google OAuth 도입은 미정이다. 공개 회원가입이나 Web 로그인 재개를 뜻하지 않는다.
독립 설정 페이지의 필요성도 미정이며 My·관리자 관리와 중복되지 않는지 먼저 검토한다.

## 3. RBAC+ABAC 논의용 매트릭스

확정 사항 외의 세부 허용·제한은 제안이다. 역할 enum 이름·DB 구조·동적 권한 편집기를 확정하지 않는다.
기존 CASL을 확장하고 서버에서 매 요청 인가한다. 속성은 실제 요구가 있는 것만 도입한다.

| 작업                                         | 일반 관리자 | 슈퍼관리자       | ABAC 조건·미정 정책                            |
| -------------------------------------------- | ----------- | ---------------- | ---------------------------------------------- |
| 콘텐츠 조회·검색                             | 허용 제안   | 허용 제안        | 활성 계정·MFA, 비공개 조회 범위                |
| 추가·작업본 수정·미리보기·승인 요청          | 허용 제안   | 허용 제안        | 대상·기준 버전, 공동 편집/담당 범위 미정       |
| 일반 관리자 변경의 승인·공개                 | 불가        | 허용             | 승인할 정확한 버전; 자기 작성분 승인 여부 미정 |
| 숨김·공개 중단·복원                          | 요청 제안   | 실행 제안        | 사유·최근 재인증·과거 공개 내용 보존           |
| 곡·앨범 물리 삭제                            | 불가 제안   | 제한적 허용 제안 | 공개 이력·참조 보호는 우회하지 않음            |
| 파형 조회·등록                               | 허용 제안   | 허용 제안        | 현재 영상 일치·교체 이력, 공개 영향 구분       |
| My·비밀번호·알림                             | 본인만      | 본인만           | 본인 여부·작업별 재인증·수신자 소유권          |
| 관리자 목록·상세·일반 관리자 초대            | 불가 제안   | 허용             | 개인정보 최소 표시·초대 유효성                 |
| 권한 변경·정지·회수                          | 불가        | 허용             | 최근 재인증·사유·마지막 사용 가능한 슈퍼 보호  |
| 슈퍼 추가·승격·회수·복구 지원                | 불가 제안   | 별도 정책 필요   | 자기 잠금·전원 잠금·전환 중 접근 상실 방지     |
| 개인정보 원문 열람·다운로드                  | 불가 제안   | 제한적 허용 제안 | 업무 필요·사유·최근 재인증·접속기록            |
| 감사 페이지 조회                             | 불가        | 허용             | 슈퍼 자신의 행위와 조회도 기록하는 안          |
| 타인 password/MFA secret 조회·감사 수정/삭제 | 불가        | 불가             | 기존 비밀 보호·감사 불변 계약                  |

승인할 버전과 공개 버전을 구분하고 변경 후 재승인, 검토 중 공개 버전 변경, 요청자 회수 시의
처리를 설계한다. 제목·영상·앨범·출처·노출·LRC 경로가 승인 우회가 되지 않도록 범위를 정한다.
이 내용은 P09 도구 확장이 아니라 작업본/공개 분리와 승인 계약이다. 숨김·대량 작업의 정책은 미정이다.

## 4. 가입·전환·My의 설계 조건

가입 흐름은 초대 → 이메일 소유 확인 → 본인 비밀번호·정보 설정 → MFA 확인 → 활성화다.
G의 일회용·만료·취소·재발송, 링크 GET 비소모, 기존 계정 자동 연결 금지 제안을 대조한다.
초대·발송 결과·계정 상태를 구분하며 상태 이름·TTL·등록 중 포기·정리 기간은 아직 정하지 않았다.
완료 직전 초대와 초대자 현재 권한을 재확인하고 MFA 완료 전 관리 권한을 주지 않는 안이다.

서비스 계정이 실제 로그인·MFA·복구 가능함을 확인하기 전 기존 접근을 회수하지 않는 전환안을 검토한다.
계정 공유 대신 개인별 관리 계정을 사용하고, 마지막 슈퍼 보호와 보호된 운영자 비상 복구를 함께 설계한다.
슈퍼에게 타인의 비밀번호·활성 QR·복구 코드를 조회시키지 않는다.

My는 Console 본인 계정을 대상으로 제안한다. 진입 재인증의 범위·TTL, 민감 작업 추가 MFA,
비밀번호/이메일 변경 후 회수는 active 계약과 함께 확정한다. 비밀번호를 URL·로그·Query cache·영속 draft에
남기지 않는다. 브라우저/암호 관리자의 저장·자동완성은 HTML 속성만으로 완전 차단할 수 없음을 구분한다.

## 5. 행동 로그·감사·개인정보

콘텐츠 변경/승인/공개/삭제/복원, 초대/권한/회수, 인증 보안 이벤트, 개인정보 조회·원문 열람·다운로드를
수집 후보로 삼는다. 수행자 ID·작업·대상 ID·시각·결과·사유·요청 식별자와 필요한 변경 이력을 연결한다.
콘텐츠 이력, 개인정보 접속기록, 보안 이벤트는 목적·보존 기간을 구분한다. 비밀번호·OTP·토큰·secret과
개인정보 원문을 자유형 metadata나 변경 전후 JSON으로 통째로 복제하지 않는다.

목록 기본 마스킹, 본인 My의 필요한 원문, 슈퍼의 업무 목적 원문 열람을 구분하는 안이다.
서버 DTO에서 최소 항목만 제공하고 UI·다운로드·로그·Sentry까지 확인한다. 가입을 위해 실명·전화번호를
자동 추가하지 않는다. 별표 개수 등 구체 마스킹 형식을 법정 고정 규칙으로 간주하지 않는다.

2026-11-01 공식 원문 확인 기준:

- [안전성 확보조치 제5조](https://www.law.go.kr/LSW/admRulSideInfoP.do?admRulSeq=2100000281400&docCls=jo&joNo=0005&joBrNo=00&dashNo=&urlMode=admRulScJoRltInfoR): 최소 차등 권한, 변경/말소, 권한 이력 최소 3년.
- [제8조](https://www.law.go.kr/LSW/admRulSideInfoP.do?admRulSeq=2100000281400&docCls=jo&joNo=0008&joBrNo=00&dashNo=&urlMode=admRulScJoRltInfoR): 접속기록 원칙 1년 이상, 5만 명 이상·민감/고유식별정보·해당 기간통신사업자 등 조건은 2년 이상, 점검·안전 보관.
- [제12조](https://www.law.go.kr/LSW/admRulSideInfoP.do?admRulSeq=2100000281400&docCls=jo&joNo=0012&joBrNo=00&dashNo=&urlMode=admRulScJoRltInfoR): 화면·인쇄·파일의 목적별 항목 최소화와 출력물 보호.
- [KISA 개발보안 가이드](https://www.kisa.or.kr/2060204/form?page=1&postSeq=5), [개발자 개인정보 보호조치 안내서](https://www.kisa.or.kr/2060301/form?lang_type=KO&postSeq=25)는 구현 점검 자료다. 게시 정보는 확인했으나 첨부 PDF 본문 검토는 남아 있다.

법적 적용 대상·시행일·실제 처리 항목을 P12 착수 때 재대조하고 법정 의무와 제품 제안을 구분한다.
Domain의 IP 30~90일 가정을 개인정보 접속기록 전체에 그대로 적용하지 않는다.

## 6. 후속 결정·완료 기준·수명

슈퍼 자기 작성분 직접 승인, 공동 편집/담당 범위, 슈퍼 추가·회수, 초대·재인증 TTL,
원문 열람 항목·보존/파기·점검 절차, 독립 설정 페이지는 미정이다. 전체 구현 순서·PR 분할은 정책 합의 후 정한다.
이번 문서화는 실제 초대·메일 발송·계정/권한/DB 변경·P12 구현이나 배포를 승인한 기록이 아니다.

완료는 UI 표시만으로 판정하지 않는다. 승인 전 공개 차단·우회 경로·동시성, 초대부터 MFA 활성화,
마지막 슈퍼 보호·회수/복귀 후 옛 접근 차단, 본인/타인 인가, 마스킹과 감사 비밀 미노출을 검증한다.
운영 수용·배포는 코드 검증과 구분한다. P12 담당자는 정책 합의 때 이 문서를 갱신하고 구현 전 active
계약으로 승격한다. 종료 시 유효 결정은 Domain/Auth·운영 안내, 실행 요약은 단계 최종 결과로 회수한 뒤
이 계획의 유지·통합을 판단한다. G 원문을 삭제하거나 과거 제안을 소급해 확정으로 바꾸지 않는다.
