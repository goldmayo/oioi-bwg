# 21. CI

> **상태:** ✅ 적용 (2026-08-21) — GitHub Actions `verify` 워크플로.
> 남은 것: branch protection 지정(웹 설정), `api:check` 스케줄 잡, Renovate.

## 원칙 — 게이트에 넣을 것의 기준 세 가지

1. **결정적** — 같은 코드면 언제 돌려도 같은 결과. flaky한 검사가 하나라도 섞이면
   빨간불이 양치기 소년이 되어 CI 전체가 무시당합니다.
2. **외부 세계 무의존** — 백엔드·네트워크가 죽었다고 머지가 막히면 안 됩니다.
3. **로컬과 같은 명령** — CI가 실패하면 개발자가 로컬에서 **같은 명령으로 재현**할 수
   있어야 합니다. CI 전용 로직은 두 번째 진실을 만듭니다.

## `verify` 스크립트 — 로컬·훅·CI의 공통 기준

```jsonc
"verify": "npm run typecheck && npm run lint && npm run lint:fsd && npm test"
```

`lint`와 `lint:fsd`는 **다른 것을 봅니다**([02. FSD](02-fsd.md)). 둘 다 넣으세요.

`format`(prettier --write)과 `build`는 verify에 넣지 않습니다 — verify는 pre-push 훅에도
쓸 것이라 빨라야 하고, 로컬에서 build까지 매번 도는 것은 과합니다. CI는 그 둘을
**별도 스텝으로** 얹습니다(아래).

## 워크플로 (`.github/workflows/verify.yml`)

```yaml
on:
  pull_request:                # 머지 전 검증 — 핵심 목적
  push:
    branches: [main, develop]  # 머지 후 상태 확인

steps:
  - checkout / setup-node (22, cache: npm)
  - npm ci                     # install 금지 — lock이 유일한 진실
  - npm run verify
  - npm run check              # prettier 드리프트
  - npm run build              # ⚠️ React Compiler(2026-08-20 활성화)는 빌드에서만 도는
                               # babel 플러그인 — typecheck·lint가 다 통과해도
                               # 빌드만 깨지는 실패 부류가 존재합니다
```

- Node 버전은 `@types/node` 계열(22)과 맞춥니다.
- **npm 메이저는 lock을 쓰는 쪽(11)과 맞춥니다** — node 22 번들 npm(10)과 11은 중첩 peer 배치
  판정이 달라 서로의 lock을 거부합니다(실측 2026-08-21, verify.yml 주석 참고). 그래서
  `npm ci` 전에 `npm install -g npm@11`이 들어 있습니다.
- **워크플로만으로는 강제력이 없습니다.** 저장소 설정 → Branch protection(Ruleset)에서
  develop·main에 required check로 `verify`를 지정해야 빨간불이 머지를 실제로 막습니다.
  (워크플로가 한 번 돌고 나면 목록에 나타납니다 — 웹에서만 가능한 설정.)

## 🚨 `api:check`는 CI 기본 경로에 넣지 마세요

옛 가이드는 "`api:check`를 CI 맨 앞에"라고 적었습니다. **그 조언은 우리 구현에 맞지 않습니다.**

| | 옛 가이드 전제 | 이 프로젝트 |
| --- | --- | --- |
| 구현 | `openapi-ts` 재생성 후 `git diff --exit-code` | **라이브 스펙을 네트워크로 받아** 스냅샷과 비교 |
| 네트워크 | 불필요 | **필요** |
| 백엔드가 죽으면 | 무관 | **빌드가 같이 죽습니다** |

코드 생성을 기각했기 때문에 판정 방식이 바뀌었고, 그 결과 CI 적합성이 반대가 됐습니다.
`scripts/api-check.mjs` 주석에도 같은 경고가 있습니다.

**대신 별도 스케줄 잡으로 돌리세요** — 하루 한 번(`on: schedule`), 실패해도 빌드를 막지 않고
알림만. 드리프트가 잡히면 `npm run api:check -- --write`로 스냅샷을 갱신하고 변경분을 사람이 봅니다.

## `spec:coverage`도 게이트로 쓰지 마세요

두 가지 이유입니다. 누락 수치를 0으로 강제하면 **의도적으로 남긴 것**(서버 API 부재 등)을
`EXCLUDED`에 억지로 등록하게 되어 그 목록의 신뢰도가 떨어지고, 애초에 목업이 gitignore라
**CI에는 입력 데이터가 없습니다.** PR 코멘트로 수치만 보여주는 용도가 맞습니다 → [15](17-spec-workflow.md).

## 확장 순서 — 거짓 빨간불 없는 것부터 한 단계씩

| 단계 | 내용 | 시점·조건 |
| --- | --- | --- |
| ✅ | verify + check + build 게이트 | 적용됨 |
| 다음 | branch protection required check | 웹 설정 — 관리자 |
| 다음 | Renovate/Dependabot | 정확 핀(2026-08-21)과 한 세트 — 봇이 "올려도 verify 통과"를 PR로 증명. **CI가 있어야 안전한 기능이라 이 순서** |
| 그 뒤 | `api:check` 스케줄 잡 | 밤마다, 게이트 아님 |
| 나중 | `npm run size`(번들 예산 → [18](20-performance.md)) | size 스크립트를 만들 때 |
| 나중 | coverage 임계치 | 컴포넌트 테스트(jsdom) 도입 후 |
| 나중 | Playwright E2E | 시나리오 목록은 감사 문서 M-10 참고 |

같은 축의 로컬 버전이 git hooks([22](22-git-hooks.md) — pre-push에 verify)입니다.
훅은 "빨리 알려주는 편의", CI는 "우회 불가능한 강제" — 대체 관계가 아닙니다.

## 의존성 업데이트

Renovate 또는 Dependabot을 붙이세요. **Vite 8 / Rolldown · TanStack 계열이 활발히 바뀌는 중**이라
없으면 6개월 뒤에 한꺼번에 올리다 고생합니다.

`@tanstack/*`의 `latest` 지정자들은 2026-08-21에 **정확 버전으로 고정**했습니다(감사 T-7) —
이제 업데이트는 자동으로 오지 않고 의도적으로만 합니다. Renovate가 그 의도적 업데이트를
PR로 만들어 주는 도구입니다. CI는 반드시 `npm ci`를 쓰세요.

## 품질 게이트 지형 (2026-08-21)

**원칙: 차단 게이트는 verify 하나. 무겁거나 변동성 있는 측정은 게이트 밖(비차단·병렬).**
로컬 훅과 CI의 겹침은 이중 안전망이지 이중 비용이 아니다 — 훅은 러너에서 안 돈다.

| 층 | 트리거 | 내용 | 성격 |
| --- | --- | --- | --- |
| pre-commit | 로컬 | lint-staged — **변경 파일만** eslint --fix·prettier | 초 단위 |
| commit-msg | 로컬 | commitlint (한국어 subject 허용). CI에 안 넣는다 — squash 머지의 최종 메시지는 PR 제목 |
| pre-push | 로컬 | typecheck — 전체 그래프라 커밋마다는 무겁고 푸시 단위가 적정 |
| **verify.yml** | PR·push(main·develop) | typecheck·lint·fsd·test·format·build·**번들 예산**(`bundle:check`) | **머지 차단** — 전체 검사 유지: FSD boundaries 같은 파일 간 규칙은 변경 파일만으로 못 잡고, typecheck는 부분 실행이 무의미 |
| perf (보류) | — | Lighthouse CI는 **도입 안 함**(2026-08-21) — 인증 벽 때문에 측정 범위가 /login 하나라 감시 가치가 얇음. 스테이징 URL 또는 로그인 스크립트로 범위가 넓어지면 "비차단 별도 워크플로 + 수동·라벨 트리거"로 재검토 |
| e2e (예정) | 처음 nightly → 안정화 후 PR 병렬 잡 | Playwright 시나리오 | CI 편입은 mock API의 러너 접근 해결 후 |
| storybook (예정) | verify 병렬 잡 | build + test-runner. VRT는 기존 보류 결정 유지 |

### 번들 예산

`vite.config`의 `build.manifest` → `scripts/bundle-report.mjs`가 경로별 초기 JS(gzip)를 계산.
상한은 `scripts/bundle-budget.json` — 초과 시 verify 실패. 원인 추적은 `npm run analyze` → `dist/stats.html`(treemap).
기준선(2026-08-21): 엔트리 167KB, 최대 경로 /work-orders 294KB, 예산 350KB.

### 리렌더 추적 (로컬 전용)

React Compiler가 자동 메모화를 담당하므로 CI 게이트는 없다. 컴파일러가 못 잡는 케이스 추적은
`npm run scan`(react-scan, dev 서버 3000 대상) — 리렌더 하이라이트·카운트.
온디맨드 CLI로만 쓴다(상시 계측은 dev 체감을 오염) — `onRender` 계측 + 렌더 예산 하네스로의
승격은 **Playwright 시나리오 도입 시 재검토**(2026-08-21 결정). Compiler가 켜져 있어 그 전엔 기대 수익이 낮다.
